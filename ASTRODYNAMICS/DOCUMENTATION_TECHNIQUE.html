1. Objectif et périmètre

Le projet entraîne un agent à poser un module lunaire dans LunarLander-v3. Le résultat attendu n'est pas uniquement un modèle : il faut aussi expliquer la démarche, conserver les expériences, exposer la décision par une API et proposer deux interfaces locales.

Résultat final

268,98 ± 37,46 sur 100 épisodes réservés, avec 96 % de réussites.

Modèle retenu

PPO, après une baseline DQN, une analyse de sensibilité et une recherche Optuna.

Applications

Une API FastAPI, une GUI Streamlit et un dashboard Streamlit, exécutés localement.

2. Architecture générale

Deux flux coexistent :

Flux hors ligne

Le notebook et les scripts Optuna entraînent puis écrivent dans artifacts/. Ces opérations sont longues mais ne sont exécutées qu'au moment des expériences.

Flux interactif

L'API charge le modèle sauvegardé. La GUI lui envoie un état à chaque pas. Le dashboard lit directement les fichiers de résultats.

3. Notebook et démarche scientifique

NB.ipynb est le document principal de la mission. Il contient les explications, le code exécuté et les sorties obtenues. Les scripts Optuna complètent le notebook pour éviter d'y placer plusieurs centaines de lignes de gestion de processus.

Déroulé général

  1. Importer les bibliothèques et fixer les seeds.
  2. Explorer les huit observations et les quatre actions.
  3. Établir une politique aléatoire puis une baseline DQN.
  4. Tester PPO et quelques variations d'un paramètre à la fois.
  5. Lire les résultats de la campagne Optuna.
  6. Comparer les candidats sur des seeds communes.
  7. Évaluer une seule fois le modèle final sur 100 épisodes réservés.
  8. Produire les tables, figures et la vidéo de démonstration.

La séparation des seeds est le point méthodologique central : les épisodes utilisés pour choisir un modèle ne sont pas ceux qui servent à publier la performance finale.

4. Modules d'optimisation

optuna_search.py — recherche large

Ce module construit une étude TPE persistée dans SQLite. Chaque essai propose dix hyperparamètres PPO. gamma est échantillonné en travaillant sur 1 - gamma, avec une échelle logarithmique.

  • SearchConfig rassemble tous les budgets.
  • sample_ppo_parameters() décrit l'espace de recherche.
  • train_and_score_seed() entraîne une seed par tranches.
  • make_objective() calcule la moyenne des deux seeds.
  • MedianPruner arrête les essais peu prometteurs.
  • export_results() produit les CSV et le résumé JSON.

Le mode --fast possède sa propre base et son propre nom d'étude. Il peut donc vérifier le code sans contaminer les 120 essais officiels.

optuna_select.py — raffinement et robustesse

La recherche large donne une bonne zone mais reste bruitée. Ce module construit une petite grille autour du meilleur gamma, puis réentraîne plusieurs finalistes avec cinq seeds nouvelles.

  • build_gamma_grid() crée neuf valeurs autour de l'optimum.
  • dedup_key() évite de valider deux fois le même réglage.
  • phase_gamma_focus() résume les trois entraînements par point.
  • phase_robustness() classe les finalistes par moyenne, écart-type et minimum.
  • run_jobs() parallélise les entraînements indépendants.

optuna_final.py — modèle livré

Le réglage gagnant est réentraîné trois fois, à 1,5 million de pas. Chaque entraînement conserve son meilleur checkpoint. Les checkpoints utilisent une plage de seeds dédiée et reproductible ; le gagnant est ensuite choisi sur le jeu de sélection.

  • train_final() entraîne, sauvegarde et évalue un candidat.
  • main() lance les trois seeds et copie le gagnant sous models/ppo_optuna/.
  • Le jeu final 10000+ n'est pas consulté pendant ce choix.
uv run python ASTRODYNAMICS/optuna_search.py --fast
uv run python ASTRODYNAMICS/optuna_search.py --trials 120 --workers 16
uv run python ASTRODYNAMICS/optuna_select.py --workers 16
uv run python ASTRODYNAMICS/optuna_final.py --workers 3

6. GUI Streamlit

La GUI possède l'environnement Gymnasium, mais pas le modèle. Cette séparation prouve que la politique est réellement consommée par HTTP.

Les deux phases d'un vol

  1. Calcul : play_episode() crée LunarLander-v3, envoie l'observation à /play, applique l'action et stocke la télémétrie.
  2. Affichage : replay_episode() recrée la même seed et rejoue les actions. Il choisit un nombre d'images adapté à la durée demandée, sans changer le résultat du vol.

Détail de gui/app.py

ÉlémentRôle

_endpoint()Adapte la route aux tests locaux ou au client HTTP réel.
check_api()Interroge /health avant un vol.

replay_episode()Produit les images RGB avec une cadence contrôlée.

Le « carburant » est un proxy : 0,30 pour le moteur principal et 0,03 pour un moteur latéral. Il sert à comparer les vols, pas à représenter des kilogrammes réels.

7. Dashboard Streamlit

Le dashboard est volontairement compact. Quatre onglets racontent la progression du projet sans dupliquer le notebook ni créer un outil de business intelligence disproportionné.

1. Synthèse

Score final, dispersion, taux de réussite et comparaison avec les références.

2. Apprentissage

Meilleur résultat par phase et courbes EvalCallback filtrables.

3. Épisodes

Récompense, moyenne glissante, issues, carburant et actions utilisées.

4. Optuna

Essais aboutis/élagués, grille gamma, importance et robustesse.

8. Données et artefacts

artifacts/ est la mémoire du projet. Les applications ne dépendent pas de l'état du notebook : elles relisent des fichiers stables. 

artifacts/
├── configs/                 configurations JSON des entraînements
├── evaluations/
│   └── <evaluation_id>/
│       ├── summary.json     résumé agrégé
│       ├── episodes.csv     une ligne par épisode
│       ├── steps.csv        une ligne par pas pour les évaluations détaillées
│       └── during_training/evaluations.npz
├── models/                  modèles SB3 sauvegardés
├── monitor/                 récompenses d'entraînement
├── tensorboard/             événements TensorBoard
├── optuna/                  bases SQLite et exports CSV
├── figures/                 graphiques exportés
├── video/                   démonstration MP4
├── gui_runs/                vols lancés depuis la GUI
├── demo_logs/               sorties des trois services
└── experiment_registry.csv  index des évaluations

Niveau expérience

experiment_registry.csv contient une ligne par évaluation : identifiant, algorithme, nombre d'épisodes, récompense moyenne, écart-type, taux de réussite, longueur et carburant moyens.

Niveau épisode

episodes.csv contient la seed, la récompense totale, le nombre de pas, l'issue, l'état final, le nombre d'utilisations de chaque action et le proxy de carburant. C'est la source principale de l'onglet « Épisodes ».

Niveau pas de temps

steps.csv conserve l'état avant et après l'action, la récompense immédiate, le cumul, les indicateurs de fin et, pour PPO, les probabilités des actions ainsi que la valeur d'état. Ce niveau est utile pour diagnostiquer un vol, mais le dashboard courant n'a pas besoin de charger ces fichiers volumineux.

10. Scénario complet de bout en bout

  1. Le notebook entraîne les modèles et écrit les artefacts.
  2. optuna_final.py copie le gagnant vers models/ppo_optuna/best_model.zip.
  3. Au démarrage, l'API charge ce fichier une seule fois.
  4. La GUI crée un environnement avec une seed choisie.
  5. Elle convertit l'observation NumPy en liste JSON.
  6. L'API valide les huit nombres, les reconvertit en float32 et appelle PPO.predict().
  7. La GUI applique l'action reçue puis recommence jusqu'à la fin.
  8. Le vol est rejoué à l'écran et sauvegardé dans gui_runs/.
  9. Le dashboard reste indépendant : il présente les évaluations hors ligne conservées dans artifacts/.
Ce flux est également parcouru par le test d'intégration de l'API sur la seed 10000 : chaque décision passe par HTTP et l'épisode doit dépasser 200 points.

11. Limites et pistes d'amélioration

  • Le simulateur simplifie fortement la physique d'un véritable alunissage.
  • Le proxy carburant est dérivé des coûts d'action, pas d'un réservoir physique.
  • L'évaluation sur 100 épisodes donne une estimation, pas une garantie absolue.
  • L'API est locale : elle n'a ni authentification, ni quota, ni supervision.
  • Le dashboard charge les fichiers à chaque exécution et ne vise pas de gros volumes.
  • La campagne Optuna reste coûteuse malgré l'élagage et le parallélisme.

Améliorations raisonnables

  • Ajouter une normalisation des observations et comparer son effet.
  • Tester d'autres architectures de réseau sur le même protocole de seeds.
  • Mesurer la latence de l'API et ajouter un petit test de charge.
  • Exporter un rapport automatique à partir du registre des expériences.
  • Conteneuriser la démonstration si un déploiement devient nécessaire.
